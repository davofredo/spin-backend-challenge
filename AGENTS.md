# AGENTS.md — Transaction Execution API

Context file for AI coding assistants. Read it fully before generating or modifying code.

## 1. Project goal

REST API that executes financial transactions (CREDIT / DEBIT) against an **external provider**,
persists the result and exposes a query endpoint. It is a backend technical challenge: the
priorities are **clean code, clear architecture, testing, resilient provider integration and
pragmatism**. The system is assumed to run at high volume (millions of transactions per day).

The service does NOT manage balances or accounts. The provider validates funds and blocks;
we only execute, record and expose transactions.

## 2. Stack (do not change without asking)

- Java 21, Spring Boot 3.x, Maven
- Spring Web, Spring Validation, Spring Data JPA
- Lombok (limited use, see section 8)
- PostgreSQL + Flyway migrations (schema is never generated by Hibernate: `ddl-auto=validate`)
- Resilience4j (timeout, retry, circuit breaker) around the provider client
- HTTP client: Spring `RestClient`
- Tests: JUnit 5, Mockito, AssertJ, `@WebMvcTest`, WireMock, Testcontainers (PostgreSQL), JaCoCo
- Single database engine everywhere (dev, tests, docker-compose): PostgreSQL. No H2.
- Optional extras: springdoc-openapi, Dockerfile + docker-compose (app + postgres + WireMock as provider)

**Do not add** Kafka, CQRS, event sourcing, Spring Cloud, or any other dependency not listed here
without asking first. Avoid over-engineering: simple and extensible beats clever.

## 3. Architecture (ports & adapters)

Dependencies point inward: `infrastructure → application → domain`. The domain has no Spring,
JPA or HTTP imports.

```
com.example.transactions
├── domain
│   ├── model        Transaction, TransactionType, TransactionStatus, Money rules
│   └── exception    domain/business exceptions
├── application
│   ├── port.in      ExecuteTransactionUseCase, QueryTransactionsUseCase
│   ├── port.out     TransactionProvider, TransactionRepository
│   └── service      use case implementations, business-rule validation
└── infrastructure
    ├── adapter.in.web           controllers, request/response DTOs, exception handler
    ├── adapter.out.provider     HTTP provider client (implements TransactionProvider)
    ├── adapter.out.persistence  JPA entities, Spring Data repos, mappers (implements TransactionRepository)
    └── config                   beans, properties, Resilience4j config
```

Rules:
- Controllers only translate HTTP <-> use case. No business logic in controllers.
- JPA entities and web DTOs never leak into the domain or application layers; map explicitly.
- The application layer depends on the `TransactionProvider` and `TransactionRepository`
  **interfaces**, never on RestClient or JPA.
- Shared application types (search criteria, page result) live in `application.model`;
  Spring Data types never leave the persistence adapter.
- Constructor injection only. No field injection.

## 4. Domain rules

Transaction fields: `id` (UUID), `accountId`, `type`, `amount`, `currency`, `description`,
`status`, `providerTransactionId`, `balanceAfter`, `createdAt`, `idempotencyKey` (nullable),
`errorCode` (nullable), `errorMessage` (nullable).

- `errorCode` / `errorMessage`: for `REJECTED` they hold the provider's `code` / `message`
  (e.g. `INSUFFICIENT_FUNDS`); for `FAILED` they hold a fixed code `PROVIDER_UNAVAILABLE` plus a short
  generic message (never raw exception text). They are null for `EXECUTED`.
- `providerTransactionId` and `balanceAfter` are null unless the provider approved the transaction.

Modeling: there is no PENDING status. A `TransactionRequest` immutable value object (id, accountId, type,
amount normalised to scale 2, currency, description, createdAt, idempotencyKey) represents what is about to
be executed. `Transaction` is built only through the factories `executed`, `rejected` and `failed`,
each taking the request plus the provider outcome. The web DTO is named differently
(e.g. `CreateTransactionRequest`) to avoid confusion with this domain type.

- **Money is always `BigDecimal`**, scale 2, never `double`/`float`. DB column `NUMERIC(19,2)`.
- `type`: `CREDIT | DEBIT`.
- `status`: `EXECUTED` (provider approved), `REJECTED` (provider rejected, e.g. INSUFFICIENT_FUNDS),
  `FAILED` (provider unreachable / timeout / 5xx / circuit open — outcome not confirmed).

### Business rules (validated in our service BEFORE calling the provider)

1. Minimum amount: amount must be strictly greater than 1.00 (<= 1.00 is rejected).
2. DEBIT maximum: amount must be <= 10,000.00 (exactly 10,000.00 is allowed). CREDIT has no limit.
3. Only currency `MXN` is supported; any other currency is rejected.

If a rule fails: do NOT call the provider, do NOT persist, return a descriptive error.
Basic input validation (missing/blank fields, null amount, unknown type) uses Bean Validation
on the request DTO; business rules live in the application/domain layer, not in annotations.

## 5. Endpoints

### POST /transactions
Flow: validate request → apply business rules → call provider → persist result → return transaction.

Request:
```json
{ "accountId": "acc-123456", "type": "CREDIT", "amount": 1500.00, "currency": "MXN", "description": "Transferencia recibida" }
```
Response (example): `id`, `accountId`, `type`, `amount`, `currency`, `description`,
`status`, `providerTransactionId`, `balanceAfter`, `createdAt` (ISO-8601 UTC). It also includes
`errorCode` and `errorMessage` when they are not null (REJECTED / FAILED); these are additive fields.

Optional header `Idempotency-Key`: if the same key is sent again, return the originally stored
transaction instead of executing again (unique index on the key column). Never call the provider
twice for the same key.

### GET /transactions
Optional query params: `accountId`, `status`, `type`, `page`, `limit`.
Filters are combinable. Pagination is mandatory: default `limit` 20, maximum 100. Order by
`createdAt` desc. Response includes items plus pagination metadata (page, limit, total).
Add DB indexes that support the filters (e.g. `(account_id, created_at)`).

## 6. External provider

Contract: `POST /provider/v1/execute`

Request: `{ accountId, type, amount, currency }`

- HTTP 200 → `{ transactionId, status: "APPROVED", balance, executedAt }` → we persist `EXECUTED`,
  `providerTransactionId = transactionId`, `balanceAfter = balance`.
- HTTP 4xx → `{ status: "REJECTED", code, message }` → persist `REJECTED` with the provider's code/message.
- HTTP 5xx, timeout, connection error, open circuit → persist `FAILED`.

Requirements:
- Everything behind the `TransactionProvider` port; the application layer knows nothing about HTTP.
- Provider base URL, connect/read timeouts, retry and circuit-breaker settings come from
  `application.yml` properties, not hardcoded.
- Explicit connect and read timeouts. Limited retries (max 2-3, with backoff) ONLY on connection
  errors / 5xx, never on 4xx. Circuit breaker around the call.
- Be careful retrying a DEBIT: a timeout does not prove the provider did not execute it. Document
  this trade-off in the README rather than hiding it.
- The provider is mocked with WireMock (stub mappings in the repo, also used by docker-compose).
  We never implement the real provider.

## 7. Error handling

Single `@RestControllerAdvice` returning RFC 7807 `ProblemDetail`.
- Bean Validation / malformed body → 400
- Business-rule violation → 422 with a clear `detail` message
- Provider unavailable (`FAILED`) → 502/503 (the FAILED transaction is still persisted)
- Unexpected → 500 without leaking stack traces
Exception policy: invalid input data (blank text, null required fields, wrong money scale) →
`InvalidTransactionDataException`; null collaborator arguments → `Objects.requireNonNull`;
business rule violations → their own domain exception (`BusinessRuleViolationException`).
Never expose internal exception messages or provider internals to the client.

## 8. Code style

- Clear names, small methods with a single responsibility, code that communicates intent.
- Prefer `record`s for DTOs and immutable value objects (no Lombok there).
- Lombok is allowed in a limited way, and ONLY these annotations:
  - `@Slf4j` for logging.
  - `@RequiredArgsConstructor` for constructor injection in services, adapters and controllers.
  - `@Getter` / `@Setter` only on JPA entities (they cannot be records). Never on domain models.
  - Do NOT use `@Data`, `@Builder`, `@Value`, `@AllArgsConstructor`, `@EqualsAndHashCode` or `@ToString`
    (especially not on JPA entities). Write them by hand if really needed.
- Domain models stay free of Lombok and are built through constructors/factory methods that enforce invariants.
- No commented-out code, no unused imports, no `System.out`. Use SLF4J, and never log sensitive data.
- Use `Clock` injection for time so it is testable.
- Short Javadoc only where the intent is not obvious from the code. English for code and comments.
- Keep it simple: no abstractions that have a single trivial use.

## 9. Testing

- Unit tests: domain rules and the use-case service (provider and repository mocked with Mockito).
  Cover boundaries: amount 1.00 (rejected) vs 1.01, DEBIT 10,000.00 (ok) vs 10,000.01 (rejected),
  non-MXN currency, CREDIT with a huge amount, provider APPROVED / REJECTED / unavailable,
  idempotent repeat.
- Web tests: `@WebMvcTest` for validation, status codes and error format.
- Provider adapter tests: WireMock for 200, 4xx REJECTED, 5xx, timeout, malformed JSON, retries
  and circuit breaker.
- Persistence/filter/pagination tests run against a real PostgreSQL via Testcontainers, applying the
  same Flyway migrations used in production. Do NOT use H2 (not even in PostgreSQL compatibility mode).
- Test naming: `shouldDoSomething_whenCondition`. Arrange-Act-Assert. One behavior per test.
- JaCoCo report enabled (`mvn verify`). Target: high coverage of domain and application layers.

## 10. Workflow

- Work in small, vertical steps and keep every step compiling with green tests.
- Small, frequent commits in Conventional Commits style (`feat:`, `test:`, `docs:`, `refactor:`).
- Do not rewrite files wholesale when a small edit is enough.
- Before adding a class, dependency or abstraction not described here, explain why and ask.
- The author must be able to explain every line: prefer simple, readable solutions over
  clever ones, and explain non-obvious decisions briefly when you make them.
